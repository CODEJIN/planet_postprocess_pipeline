# 토성 고리 관련 검출 오류 — 이번 세션 수정 기록

이번 세션에서 진행한 수정 두 건과, 아직 손대지 않은/검증 못한 부분을 정리한다.
공통 원인: 토성 고리(disk 지름의 ~2.2배까지 뻗음)가 여러 곳의 "행성 원반 검출" 로직에서
원반과 한 덩어리로 잡혀, 반경/형태 관련 계산이 전부 틀어짐.

---

## 1. Step 1 — SER Crop 행성 미검출 (커밋 완료: `6525e8f "saturn ser crop fix"`)

### 증상
GUI Step 1 미리보기에서 토성이 전혀 감지되지 않음(전 프레임 거부). 금성 초승달 모양은 정상 감지됨.

### 원인
[pipeline/modules/planet_detect.py](../pipeline/modules/planet_detect.py) `analyze_planet()`의 원형성 검사(`aspect_ratio_limit`, 기본 0.2 → 짧은변/긴변 ≥ 0.8 요구)가
triangle 임계값으로 얻은 "원반+고리" 하나의 연결요소 바운딩박스에 대해 계산됨. 고리 포함 바운딩박스는 가로가 세로의 2배 이상이라 항상 탈락.
2026년 8월 현재 고리 기울기가 거의 최소(2025년 3월 고리평면통과 직후)라 문제가 더 심함.

### 시도했다가 버린 방법
Morphological opening(침식→팽창)으로 얇은 고리를 제거하려 했으나, **실측 데이터에서 거의 효과 없음** 확인
(면적 4%만 감소). 단일 원시 프레임은 노이즈가 심해서 고리가 이진화 마스크에서 예상보다 훨씬 두껍게 잡히기 때문.

### 최종 수정
블롭 내부 픽셀 밝기의 percentile(기본 60%)로 재이진화 → 더 밝은 원반 코어만 남기고,
원형성/직선-edge 검사는 이 코어에 대해 수행. 경계(클리핑)/최소지름/중심점은 기존처럼 원반+고리 전체 bbox 사용.
목성처럼 고리 없는 꽉 찬 원반은 opening 대신 percentile을 써도 거의 영향 없음(면적 대부분 유지) — 이 단계에서는 "판정만" 하면 되므로 문제 없었음
(※ 아래 2번 항목에서 이 가정이 반경 정밀도가 필요한 다른 함수에서는 깨진다는 걸 확인함).

### CH4(메탄 밴드) 필터는 별도 처리
CH4 밴드는 대기 메탄 흡수 때문에 원반이 고리보다 **어둡게** 나옴(물리적으로 잘 알려진 특성) — "밝은 부분=원반" 가정이 반전됨.
percentile 방식이 원천적으로 안 통해서, `filter_name == "CH4"`일 때 원형성/직선-edge 검사 자체를 건너뛰도록 처리
(경계+최소지름+사이즈일관성 체크만 적용).

### 검증 결과 (50개 SER 파일, 152,378 프레임 전체 실행)
| 필터 | 거부율 (수정 전 → 후) |
|---|---|
| R | 100% → 1.8% |
| G | 100% → 0.5% |
| B | 100% → 1.1% |
| CH4 | 100% → 3.2% |
| IR | 100% → 22.0% (다른 필터보다 높음 — 세션 중 IR 촬영 시상 자체가 더 나빴을 가능성, 알고리즘 문제로 보이진 않음) |
| 전체 | 100% → 6.2% |

목성 실측 데이터로 회귀 없음 확인(100% → 100%).

### 변경 파일
- `pipeline/modules/planet_detect.py` — 핵심 로직
- `pipeline/config.py` — `SerCropConfig.core_percentile` (기본 60.0) 추가
- `pipeline/steps/ser_crop.py` — CH4 자동 감지 → `skip_shape_check=True` 전달
- `gui/widgets/ser_preview.py` — GUI 미리보기도 동일 CH4 예외 반영

## 2. `derotation.py` `find_disk_center()` — 원반 반경/편평률 오염 (Phase 1, **미커밋, 워킹트리에 남아있음**)

### 문제 인지 경위
사용자 요청으로 Step 5 de-rotation이 토성에 적용 가능한지 분석하다가, `find_disk_center()`가
Otsu 이진화 후 `cv2.fitEllipse`를 **원반+고리 컨투어에 직접** 적용한다는 걸 발견.

`find_disk_center()`는 derotation.py 자체 외에도 `derotate_stack.py`(Step 5, 10곳+), `lucky_stack.py`(Step 2,
AP그리드 크기/배치·품질마스크·프레임별 안정화, 수십 곳), `composite.py`/`rgb_composite.py`(Step 6),
`wavelet.py`/`wavelet_master.py`(Step 5/7 페더링), `gif.py`(Step 8), `aperture_contrast.py`,
GUI 미리보기 2곳 등 **~40곳에서 공유하는 핵심 함수**임.

### 실측 확인 (수정 전)
토성 R필터 SER 60프레임 평균 이미지에 대해:
- Otsu 이진화 마스크 → 원반+양쪽 고리가 하나의 blob
- `cv2.fitEllipse` 결과: `semi_major=129px, semi_minor=59px` (장축 지름 258px)
- 실제 원반 지름은 시각적으로 ~130~140px(반경 ~65~70px)뿐 — 고리가 반경을 거의 2배로 부풀림
- 안전장치인 `_gradient_disk_r()`(그래디언트 기반 립 재탐색)도 무력화됨: 오염된 r_rough(129px) 기준
  탐색창(96.7~167.7px)이 실제 립(~65~70px)보다 훨씬 바깥이라 탐색 범위 자체가 빗나가, 8개 이상의 유효 ray를
  못 찾고 조용히 r_rough 그대로 반환.

이 오염이 `spherical_derotation_warp`의 warp 반경/오블레이트 비율, `auto_detect_pole_pa`의 "원반 내부" 마스크,
cubic/linear 보간 전환 경계, per-frame 서브픽셀 정렬(`limb_center_align`) 등으로 전부 전파됨.

### 시도 1 (실패 → 되돌림): 무조건 percentile 재이진화
Step 1과 같은 방식(무조건 percentile 60%로 재이진화 후 그 위에서 fitEllipse)을 그대로 적용했더니,
**고리가 전혀 없는 목성에서도 회귀 발생**: semi_a가 104px → 67.5px로 35% 축소.
원인 — limb darkening 때문에 **어떤 원반이든** percentile로 자르면 그냥 "더 작고 밝은 코어"만 남지,
이건 고리 제거가 아니라 같은 원반을 더 작게 도려내는 것뿐임. 실측: 목성 blob은 percentile 60%에서 면적의
40%만 남음(반경으로는 약 63%, 즉 대략 37% 축소) — Step 1에서는 "판정(accept/reject)"만 하면 됐지만
`find_disk_center`는 **반경 절댓값 자체**가 결과물이라 이 축소가 그대로 오차가 됨.

### 최종 수정 (현재 코드 상태)
1. 먼저 **원본(고리 포함) blob 그대로 fitEllipse**를 수행해 raw aspect ratio(짧은축/긴축)를 구함.
2. raw aspect < 0.80일 때만 (실제 타원체 행성은 이보다 낮게 안 나옴 — 목성 실측 ~0.94, 토성 고리 없는 원반
   실측 ~0.88~0.91) percentile 코어 격리를 적용 → 목성/화성/금성은 원래 로직 그대로 무변화, 회귀 없음.
3. 고리 격리된 코어는 그 자체로 과소추정(더 높은 임계값 효과)이므로, 이 경우에만
   `_gradient_disk_r`의 탐색창을 (0.75~1.30배) → (0.6~1.8배)로 넓혀 실제 립을 다시 찾게 함.
4. 편평률(semi_b/semi_a)은 코어 타원에서 측정한 비율을 보존하고, 절대 크기만 그래디언트 재탐색으로 보정.

### 검증 결과 (실측)
| | 수정 전 | 수정 후 |
|---|---|---|
| 토성 R필터 | semi_a=129px, b/a=0.457 | semi_a=66px, b/a=0.882 (실제 ≈0.902) |
| 토성 G/B/IR (4개 파일) | 동일 패턴으로 깨짐 | semi_a 63~67px, b/a 0.82~0.91, 각도 일관됨 |
| 목성 (회귀 확인) | semi_a≈104px, b/a≈0.939 | semi_a=104.0px, b/a=0.939 — **완전 동일** |
| `limb_center_align` 서브픽셀 정렬 | — | 인위적 3.7px 이동 → 3.93px 복원(오차 0.2px) |
| `fixed_threshold=20` 경로(Step 2 방식) | — | semi_a=68.2px, b/a=0.854 — Otsu 경로와 일관 |
| CH4 | semi_a=148.6px, b/a=0.159(엉망) | semi_a=148.6px, b/a=0.159 — **그대로 엉망**(아래 참고) |

### 변경 파일
- `pipeline/modules/derotation.py` — `find_disk_center()`에 로직 추가(~64줄), 모듈 상단 docstring에
  토성/CH4 관련 노트 추가. **다른 파일은 변경 없음** (전부 반환값만 소비하므로).

## 3. 확인했지만 손대지 않은 것 — 알려진 한계 / 잔여 위험

사용자가 "문제가 많은 거 같다"고 지적한 부분들을 정리하면, 이번 세션에서 실제로 **검증까지 끝낸 건 `find_disk_center()`
단일 함수의 반환값 정확도뿐**이고, 그 값을 소비하는 ~40개 호출부가 실제로 이걸로 잘 작동하는지는 대부분 미검증이다.

1. **CH4 필터는 여전히 완전히 깨져 있음.** `find_disk_center()`가 이 경우 원반을 못 찾는다는 걸 알고 docstring에
   명시만 해뒀을 뿐, 실제 처리(형제 필터에서 지오메트리 빌려오기 등)는 하지 않음 — 원래 계획한 "Phase 2".
   CH4로 Step 5(de-rotation)를 그대로 돌리면 지금도 터지거나 엉뚱한 결과가 나올 것.

2. **`_gradient_disk_r`의 ray 탐색이 고리 평면과 겹치는 각도에서 여전히 오염될 가능성.** 링이 거의 edge-on이라
   영향받는 각도 폭이 좁아서 기존 median±2σ 아웃라이어 제거가 충분할 거라 "추정"했지만, 여러 세션/시상 조건에서
   반복 검증하진 않음.

3. **`satellite_tracker.py`의 기존 캘리브레이션이 어긋날 수 있음.** 이 모듈은 `find_disk_center`의 기존(오염된) 편향을
   보정하는 `cx_offset` 캘리브레이션 값을 갖고 있는데(그림자-통과 캘리브레이션 기반), `find_disk_center`의 동작이
   바뀌었으니 이 오프셋이 더 이상 맞지 않을 수 있음. 사용자가 애초에 "위성/그림자 처리는 제외하고 보자"고 했던
   부분이라 이번 세션에서 재검토하지 않음 — **다음에 위성 트래킹을 건드릴 때 반드시 재확인 필요.**

4. **Step 2 (lucky_stack.py)의 AP 그리드/품질마스크가 실제로 좋아졌는지 미검증.** `find_disk_center` 반환값이
   정확해졌다는 것만 확인했지, 그 값으로 만들어지는 AP 그리드 배치나 품질 점수 순위가 토성 데이터에서 실제로
   개선됐는지 시각적으로/정량적으로 확인하지 않음.

5. **Step 5~8 엔드투엔드 미검증.** 실제 토성 세션으로 Step 2→8을 끝까지 돌려서 최종 결과물(스택/샤프닝/합성/GIF)이
   시각적으로 좋아졌는지 확인 안 함 — 지금까지는 전부 `find_disk_center()`를 단독으로 호출해서 숫자만 검증한 것.

6. **`_gradient_disk_r` 탐색창 확장(0.6~1.8배)과 percentile 60%, aspect 게이트 0.80은 이번 세션에서 얻은 소수
   샘플(토성 세션 1개, 목성 세션 1개)로 튜닝한 값.** 다른 촬영 조건(초점거리, 노출, 시상)에서도 일반화되는지는
   추가 검증 필요.

원래 계획했던 3단계 중 **Phase 1(핵심 함수 수정)만 완료**, Phase 2(CH4 지오메트리 공유)와 Phase 3(엔드투엔드 검증)은
착수하지 않음.
